# ADR-0048 — Coordenar bootstrap por um serviço de inicialização

Status: Aceito

## Contexto

O bootstrap histórico rodava em `create_app()` fora de TESTING, conforme [ADR-0010](ADR-0010.md). O Compose inicia
quatro workers, então esse comportamento permitia concorrência de migrations e seeds em banco vazio. A implementação
validada removeu os efeitos de banco da factory e adicionou o comando explícito `flask bootstrap-db` e o serviço
`api-init`, do qual a API aguarda conclusão bem-sucedida.

## Decisão

Executar migrations pendentes e seeds em um único serviço `api-init`, depois de o banco estar saudável.
A API depende da conclusão bem-sucedida desse serviço antes de iniciar os workers. Disponibilizar o bootstrap
por comando explícito e retirar os efeitos de banco da criação da aplicação e do startup dos workers.

A coordenação cobre um projeto Compose com um único init. Não oferece exclusão distribuída entre diferentes
hosts ou execuções manuais concorrentes; o fluxo operacional deve serializar essas execuções.
Esta decisão substitui [ADR-0010](ADR-0010.md).

## Consequências

- Positivas: Evita disputa de migrations pelos workers e separa inicialização do banco da criação da aplicação.
  O comando pode ser reutilizado pela futura pipeline.
- Negativas ou limitações: Exige configurar a ordem de inicialização e atualizar os comandos de execução local.
  Falha do init bloqueia a API nova; não implica rollback automático de DDL nem exclusão entre projetos distintos.

## Alternativas Consideradas

Bootstrap no entrypoint da API antes do Gunicorn: apresentado como alternativa mais simples, mas executa o
bootstrap por container iniciado. O usuário escolheu o serviço separado com espera de sucesso.
Manter o bootstrap por worker: é o estado atual, com risco de concorrência comprovado no histórico operacional.

Referência: [Compose — ordem de inicialização](https://docs.docker.com/compose/how-tos/startup-order/).
